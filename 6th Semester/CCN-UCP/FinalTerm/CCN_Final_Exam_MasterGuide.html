TCP Deep Dive — Everything You Must Know

📋 TCP Header Fields — Memorize All of These
FieldSizePurpose — What the teacher asks about
Source Port16 bitIdentifies sender application; used for demultiplexing
Destination Port16 bitIdentifies receiver application; used for demultiplexing
Sequence Number32 bitByte-stream number of FIRST data byte in this segment (NOT segment number)
Acknowledgement Number32 bitSeq# of NEXT byte expected from the other side (cumulative ACK)
Header Length4 bitHeader length in 32-bit words; typical = 5 (20 bytes)
Flags (6 bits)6 bitSYN=setup, FIN=teardown, ACK=ack valid, PSH=push, URG=urgent, RST=reset
Receive Window16 bitFlow control — how many bytes receiver is willing to accept (rwnd)
Checksum16 bitError detection over entire TCP segment
Urgent Pointer16 bitUsed with URG flag; points to end of urgent data

Compare with UDP: UDP has only 4 fields (src port, dest port, length, checksum). TCP's additional fields = Seq#, ACK#, Header length, Flags, Receive Window, Urgent Pointer → these provide reliable delivery, flow control, connection management.

🔢 Sequence & Acknowledgement Numbers — The Most Commonly Failed Topic
  • TCP assigns a sequence number to EVERY BYTE, not every segment
  • Seq# in segment header = byte-stream number of the FIRST byte of data in that segment
  • ACK# = sequence number of the NEXT byte Host B expects from Host A
  • If Host A sends 500 KB file with MSS=1000 bytes: segment 1 Seq#=0, segment 2 Seq#=1000, segment 3 Seq#=2000 etc.
  • ISN (Initial Sequence Number) is chosen randomly at connection setup
Example (from Assignment 3 Q3b): ISN=200, Seg1=20 bytes, Seg2=40 bytes, Seg3=15 bytes Seg1: Seq=200, ACK=? (whatever server ISN+1 is) Seg2: Seq=220 (200+20), Seg3: Seq=260 (220+40) After Seg1: receiver sends ACK=220 (next expected) After Seg2: receiver sends ACK=260 After Seg3: receiver sends ACK=275
⏱️ RTT Estimation & Timeout — The Calculation Question

These formulas appear EVERY time (both Assignment 3 and the practice problem in Week 10 slides):

EstimatedRTT = (1-α) × EstimatedRTT + α × SampleRTT [α = 0.125 typically] DevRTT = (1-β) × DevRTT + β × |SampleRTT - EstimatedRTT| [β = 0.25 typically] TimeoutInterval = EstimatedRTT + 4 × DevRTT

Order of calculation: (1) compute new DevRTT first, (2) then compute new EstimatedRTT, (3) then compute TimeoutInterval. Students who reverse the order lose all marks.

Example (Assignment 3 Q2): Initial EstRTT=103ms, DevRTT=6ms, α=0.125, β=0.25 --- After SampleRTT = 110ms --- DevRTT = (0.75)(6) + (0.25)|110-103| = 4.5 + 1.75 = 6.25ms EstRTT = (0.875)(103) + (0.125)(110) = 90.125 + 13.75 = 103.875ms Timeout = 103.875 + 4(6.25) = 103.875 + 25 = 128.875ms --- After SampleRTT = 180ms --- DevRTT = (0.75)(6.25) + (0.25)|180-103.875| = 4.6875 + 19.03 = 23.72ms EstRTT = (0.875)(103.875) + (0.125)(180) = 90.89 + 22.5 = 113.39ms Timeout = 113.39 + 4(23.72) = 113.39 + 94.88 = 208.27ms
🤝 TCP 3-Way Handshake — Must Be Able to Draw This
  • Step 1 (Client → Server): SYN segment, SYN flag=1, client chooses ISN (e.g. ISN_c), no data
  • Step 2 (Server → Client): SYN-ACK segment, SYN=1, ACK=1, server chooses ISN_s, ACK# = ISN_c + 1
  • Step 3 (Client → Server): ACK segment, ACK=1, SYN=0, ACK# = ISN_s + 1, MAY contain data

Connection close is 4-way: Client FIN → Server ACK → Server FIN → Client ACK (then wait)

📦 TCP Flow Control
  • Receiver advertises free buffer space using the rwnd (Receive Window) field in TCP header
  • Formula: RcvWindow = RcvBuffer - [LastByteRcvd - LastByteRead]
  • Sender constraint: LastByteSent - LastByteAcked ≤ min(cwnd, rwnd)
  • This guarantees receiver buffer will not overflow

TCP Congestion Control — The Most Likely Final Exam Topic

⚠️ Assignment 3 Q4 and Q5 are almost certainly in the final exam

The entire Assignment 3 is CLO-3 (final). Q4 asks to analyze a TCP Reno graph with 6 sub-questions. Q5 asks to draw the cwnd graph and calculate time in SS phase. Expect very similar questions in the final exam.

📊 Three Phases of TCP Congestion Control
PhaseWhen does it start?How does cwnd grow?When does it end?
Slow Start (SS) Connection begins, OR after timeout Exponential: cwnd doubles every RTT (add 1 MSS per ACK) When cwnd reaches ssthreshold, OR loss event occurs
Congestion Avoidance (CA) When cwnd ≥ ssthreshold Linear: cwnd += 1 MSS per RTT (add MSS/cwnd per ACK) When loss event occurs
Fast Recovery (TCP Reno) After triple duplicate ACK Linear (CA) from cwnd/2 When timeout or new ACK received
🔄 TCP Reno vs TCP Tahoe — Key Difference
TCP Tahoe
  • On timeout: cwnd = 1 MSS, SS from start
  • On 3 dup ACKs: cwnd = 1 MSS, SS from start
  • Treats both events the same (aggressive)
TCP Reno (more common)
  • On timeout: cwnd = 1 MSS, SS from start
  • On 3 dup ACKs: cwnd = cwnd/2, then CA (Fast Recovery)
  • 3 dup ACKs = network can still deliver some pkts → less severe
📈 Reading a TCP Reno Congestion Window Graph — Step by Step

This is the exact graph in Assignment 3 Q4. Here is how to analyze it systematically:

  • Step 1 — Find Slow Start intervals: Look for exponential growth (1→2→4→8 doubling pattern). Slow Start starts at cwnd=1 MSS and runs until either ssthreshold is hit OR loss occurs.
  • Step 2 — Find CA intervals: Look for linear growth (+1 MSS per RTT). These come after ssthreshold is reached.
  • Step 3 — Find timeout events: cwnd drops suddenly to 1 MSS. ssthreshold is set to half of cwnd at time of loss.
  • Step 4 — Find triple dup ACK events: cwnd drops to HALF (not to 1). Then continues linear growth. This is Fast Recovery.
  • Step 5 — Identify ssthreshold values: New ssthreshold = cwnd/2 at time of loss. It can change multiple times.
For Assignment 3 Q4 graph analysis (approximate, based on the graph shown): Rounds 1-6: Slow Start (cwnd: 1,2,4,8,10,11 — exponential then slows near ssthresh) Around Round 7: Loss event by timeout (cwnd drops to 1, ssthresh = cwnd/2 ≈ 6-7) Rounds 8-14: SS again from 1, CA after ssthresh Round 14 or so: Triple dup ACK (cwnd halved, fast recovery → CA) Note: Look at the ACTUAL graph image — identify every drop point precisely.

🔁 Fast Retransmit — Key Mechanism
  • If sender receives 3 duplicate ACKs for same data → retransmit unACKed segment with smallest seq# immediately
  • Does NOT wait for timeout (timeout is too slow)
  • Duplicate ACK = receiver got out-of-order segment, sends ACK for highest in-order byte it has
  • 3 dup ACKs = "implicit NAK" for the missing segment

Go-Back-N and Selective Repeat

📊 GBN vs SR Comparison Table
PropertyGo-Back-N (GBN)Selective Repeat (SR)
Max window sizeN ≤ 2^k - 1N ≤ 2^k / 2
ACK typeCumulative (ACKs all up to n)Individual (ACKs each pkt)
TimerOne timer for oldest unACKed pktSeparate timer per unACKed pkt
On timeoutRetransmit pkt n AND all higher in windowRetransmit only the unACKed pkt
Out-of-order pktsDISCARD (no receiver buffer)BUFFER for in-order delivery
Receiver bufferNot neededRequired (window size N)
⚠️ SR Dilemma — Understand This for MCQs / T/F Questions
  • If you use k bits for seq numbers, you have 2^k seq numbers (0 to 2^k-1)
  • For SR: window size N must be ≤ 2^k / 2. Why? If N > 2^k/2, the receiver cannot distinguish between a new packet and a retransmitted duplicate.
  • For GBN: window size N must be ≤ 2^k - 1. The receiver doesn't buffer, so one reserved seq# is enough.
  • Example: k=3 bits → 8 seq numbers. GBN max window = 7. SR max window = 4.

✂️ IP Fragmentation — The Calculation You Must Know

When a datagram is larger than link MTU, it is fragmented. All fragments except the last have More flag = 1. Last fragment has More flag = 0. Offset is in 8-byte units.

Example from slides: 4000 byte datagram, MTU = 1500, ID = 777 IP header = 20 bytes. Data payload = 4000 - 20 = 3980 bytes. Each fragment can hold: 1500 - 20 = 1480 bytes of data (1480 must be multiple of 8 for fragmentation offset — ✓ 1480/8 = 185) Fragment 1: Length=1500, Offset=0, More=1, ID=777, Data=1480 bytes Fragment 2: Length=1500, Offset=185, More=1, ID=777, Data=1480 bytes (1480/8=185) Fragment 3: Length=1040, Offset=370, More=0, ID=777, Data=1020 bytes (2960/8=370) Check: 1480 + 1480 + 1020 = 3980 = original payload ✓

Trap: Offset is computed as (cumulative data bytes before this fragment) / 8, NOT total length / 8.

🔀 Forwarding vs Routing — Conceptual Question
  • Forwarding: Moving a packet from input port to correct output port at a SINGLE router. Uses forwarding table. Fast, done in hardware.
  • Routing: Determining the end-to-end PATH through the network. Runs routing algorithms (Dijkstra, Bellman-Ford). Builds routing tables → populates forwarding tables.
  • Analogy: Routing = planning your trip. Forwarding = making a turn at a single intersection.
🔍 Longest Prefix Matching
  • When router looks up destination IP in forwarding table, it matches the longest prefix that matches the destination address
  • Example: dest addr 11001000 00010111 00011000 10101010 matches both prefix "11001000 00010111 00011000" (26 bits) and "11001000 00010111 000110" (22 bits). Router uses the 26-bit match (longest).
🌐 Additional Final Topics (Weeks 13-16, from course outline)
DHCP (Dynamic Host Config)
  • Auto IP address allocation
  • 4 messages: Discover, Offer, Request, ACK
  • Provides: IP, subnet mask, default GW, DNS server
NAT (Network Address Translation)
  • Maps private IPs to single public IP
  • Uses port numbers to distinguish internal hosts
  • NAT table: (private IP:port) ↔ (public IP:port)
ICMP
  • Error reporting for IP (not data transport)
  • Used by ping (echo request/reply) and traceroute
  • TTL exceeded → ICMP Time Exceeded message
IPv6
  • 128-bit addresses (vs 32-bit IPv4)
  • No fragmentation by routers
  • No checksum in header
  • Transition: tunneling, dual stack

Complete Formula & Quick Reference Sheet

📐 Delay Formulas (From Midterm — Also in Final)
Transmission Delay = L / R (L = packet size in bits, R = link rate in bps) Propagation Delay = d / s (d = distance in meters, s = propagation speed ~3×10^8 m/s) Total End-to-End Delay = Tx_delay(all links) + Prop_delay(all links) + Processing_delay + Queuing_delay For N packets sent back-to-back: Total delay = (N-1) × L/R_first_link + delay_for_last_packet Throughput = Min(R1, R2, ..., Rn) = bottleneck link rate Average Throughput = file_size / total_transfer_time
⏱️ TCP RTT & Timeout Formulas
EstimatedRTT = (1 - α) × EstimatedRTT + α × SampleRTT [α = 0.125] DevRTT = (1 - β) × DevRTT + β × |SampleRTT - EstimatedRTT| [β = 0.25] TimeoutInterval = EstimatedRTT + 4 × DevRTT ORDER: Compute DevRTT first → then EstimatedRTT → then Timeout
🔢 TCP Congestion Control Key Values
Initial: cwnd = 1 MSS, ssthreshold = large value (e.g. 64 KB) Slow Start: cwnd doubles each RTT (add 1 MSS per ACK received) Congestion Avoidance: cwnd += 1 MSS per RTT On Timeout (both Reno and Tahoe): ssthreshold = cwnd / 2 cwnd = 1 MSS → restart Slow Start On Triple Dup ACK (TCP Reno): ssthreshold = cwnd / 2 cwnd = cwnd / 2 → enter Fast Recovery (linear growth = CA) On Triple Dup ACK (TCP Tahoe): ssthreshold = cwnd / 2 cwnd = 1 MSS → restart Slow Start TCP Send Rate ≈ cwnd / RTT (bytes/sec) Average Throughput (simplified) ≈ 0.75 × W / RTT (W = window size at loss)
✂️ IP Fragmentation Formulas
Data per fragment (not last) = MTU - 20 bytes (header) [must be multiple of 8] Fragment Offset = (cumulative bytes before this fragment) / 8 More flag = 1 for all fragments except last (last = 0) All fragments have same Identification number as original datagram Reassembly: happens only at final destination
🪟 Window Size Constraints
Go-Back-N: N ≤ 2^k - 1 (k = number of bits in seq# field) Selective Repeat: N ≤ 2^k / 2 TCP Flow Control: LastByteSent - LastByteAcked ≤ min(cwnd, rwnd) TCP RcvWindow = RcvBuffer - [LastByteRcvd - LastByteRead]
🌐 Key Port Numbers & Protocol Values
HTTP: port 80 HTTPS: port 443 DNS: port 53 (UDP) SMTP: port 25 FTP: port 21 Telnet: port 23 SSH: port 22 Echo: port 7 IP Protocol field: TCP = 6, UDP = 17, ICMP = 1 DNS record types: A (hostname→IP), NS (domain→nameserver), MX (domain→mailserver), CNAME (alias→canonical) Well-known ports: 0-1023 | Registered: 1024-49151 | Ephemeral: 49152-65535
📡 HTTP Delay Formulas
Non-persistent HTTP (serial): 2 RTT + Tx_time per object Non-persistent HTTP (parallel): 2 RTT + Tx_time (all objects load in parallel) Persistent HTTP (serial within server): - 1 RTT for TCP handshake to server - 1 RTT + Tx_time for each object (no new TCP for each) - For objects on DIFFERENT servers: add 1 RTT (new TCP connection) per new server General formula for persistent HTTP with N objects across M servers: Total = M × (1 RTT for TCP setup) + N × (1 RTT + Tx_time per object)
🔑 Important MCQ/T/F Facts to Memorize
  • NS record in DNS → gives HOSTNAME of nameserver (NOT IP address). Type A gives IP address.
  • Routing at NETWORK layer. Transport layer provides process-to-process delivery.
  • Circuit switching has dedicated path. Packet switching does NOT.
  • IP fragmentation is done by ROUTERS but reassembly is done only at DESTINATION HOST.
  • UDP does NOT provide reliability, flow control, or congestion control.
  • TCP is full-duplex (data flows both directions simultaneously on same connection).
  • In GBN, receiver DISCARDS out-of-order segments (no buffering). In SR, receiver BUFFERS them.
  • TTL in IP header is decremented by 1 at each ROUTER (not host).
  • The "More" flag in IP fragmentation: 1 means more fragments follow; 0 means this is the LAST fragment.
  • TCP sends ACK using cumulative acknowledgement — ACK# = next expected byte.
  • 3 duplicate ACKs trigger fast retransmit WITHOUT waiting for timeout.
  • TCP Reno on 3-dup-ACK: cwnd = cwnd/2. TCP Tahoe: cwnd = 1 MSS regardless.
  • ssthreshold is set to cwnd/2 BOTH on timeout AND on triple dup ACK.
